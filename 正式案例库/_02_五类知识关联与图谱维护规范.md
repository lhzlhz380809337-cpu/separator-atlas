# 五类知识关联与图谱维护规范

版本：1.0｜编制日期：2026-10-11｜适用对象：本项目的初始知识、知识图谱、现场经验教训卡、优秀专项与客诉 FTA。

配套阅读：[案例报告转 Markdown 入库规范](./_01_案例报告转Markdown入库规范.md)。本文回答：知识之间怎样连接，什么关系可以用于分析，案例如何补充或修正关系，模型怎样沿这些关系追问与验证。

**知识图谱应保存“为什么有关、在什么条件下有关、怎样判断这条关系在当前问题中是否成立”。连线多不是目标；能区分候选原因、指出下一项有用检查，才是分析价值。**

本文前半部分可直接作为人工整理与审核规则，后半部分给出后续程序扩展的数据约定。新增约定不代表程序已经具备相应功能；当前仅新增说明文件，没有修改加载器、图谱、模型流程或发布范围。

## 1. 五类知识共用一张关系网络

| 类别 | 提供什么 | 应与什么关联 |
|---|---|---|
| 初始知识 | 术语、工序、材料、物性、检测方法、通用原理 | 对应概念；为机制解释和判别检查提供基础 |
| 知识图谱 | 工序与结构、物性、缺陷、下游表现之间的有条件关系 | 正文解释、适用条件、检查方法、案例证据、控制点 |
| 现场经验教训卡 | 现场现象、有效或无效排查、易误判点 | 涉及的概念、被支持或质疑的关系、判别检查及适用范围 |
| 优秀专项 | 问题定义、原因验证、试验方法、效果与维持 | 机制关系、证据组、控制点、关联经验卡和标准化建议 |
| 客诉 FTA | 顶事件、失效路径、事件之间的逻辑 | 对应概念、分支检查、证据与排除条件、相关改善措施 |

例如，“油斑”概念可以连接原理文章、CCD 实物对应的经验卡、一个经过验证的改善专项，以及某棵 FTA 中相关的事件。但“都提到油斑”只能说明主题接近，不能说明原因相同。

五类知识不是五个互不相通的数据库，也不是从第 1 类到第 5 类可信度递增。可信程度应落实到每个判断和证据，不能只给整篇文章一个“权威”标签。

## 2. 当前程序的真实关联方式

### 2.1 目前读哪些位置

| 位置 | 当前用途 | 新增内容如何生效 |
|---|---|---|
| `knowledge/*/index.json` | 初始知识目录 | 正文放在 `knowledge/` 内并登记；`file` 路径相对 `knowledge/` 根目录，如 `base/extraction_drying.md`，不是相对索引所在子目录 |
| `知识图谱/index.json` | 详细图谱文章目录 | 正文与目录一起更新；相对路径以“知识图谱”为根 |
| `graph/*.json` | 概念节点与机制关系 | 更新真实节点和关系字段，并同步相应 Markdown |
| `知识投递/` | 自建 MD/TXT | 扫描符合规则的文件，生成文章节点并参与检索 |
| `agent/playbooks.json` | 通用分析剧本 | 独立维护问题、候选假设、检查与验证步骤 |
| `正式案例库/` | 当前新设的主稿与规范目录 | **尚未接入加载、检索或通用导出** |

正式案例库中的文件目前只是保存在本机。当前要试用整理后的案例，可以按配套规范制作投递副本；后续正式接入应直接读取唯一主稿，避免长期维护两份内容。

### 2.2 目前有哪些线

| 当前关联 | 来源 | 实际意义 | 不能当作什么 |
|---|---|---|---|
| 机制线 `mechanism` | `graph` 中的 `edges` | 两个概念之间已编制的有条件作用关系 | 本次问题已经确认的因果 |
| 解释线 `explains` | 概念节点的 `article_ids` | 某篇文章解释该概念 | 文章全部内容都已验证 |
| 指定关联 `explicit` | 自建文章的 `links` 或 `[[...]]` | 作者主动指出内容有关 | 自动建立的正式因果边 |
| 主题关联 `topic` | 自建文章正文出现确切概念名称 | 术语匹配，最多连接 8 个概念 | 同名即同原因、同测法、同适用条件 |

`[[...]]` 当前可匹配：**概念的完整名称、文章标题、文章 ID、文章别名**。匹配是精确的；概念内部 ID（如 `base_oilspot`）和星球显示用的 `doc:` 前缀不是这里可用的通用目标格式。未知目标暂不连线，不代表程序自动判断其技术错误。

同名标题或重复别名可能使匹配指向错误对象。因此案例标题加入匿名编号，别名保持唯一；不要把“油斑”这种既有概念名作为某篇案例的唯一别名。

`links` 顶部字段按逗号和顿号分隔，包含这些标点的标题改用文章 ID，或在正文使用 `[[完整标题]]`。使用 `[阅读文章](相对路径.md)` 只是普通文件链接，不会因此自动形成程序中的图谱关系。

### 2.3 当前检索不是完整的图推理引擎

当前会根据关键词、术语和剧本检索文章片段，再补充相关的 `graph` 机制关系。星球中的文章主题线不等于已经参与多步因果推理，也不会自动把整张网络全部送给模型。

当前尚未实现：正式案例注册、逐条证据状态计算、条件过滤的完整图遍历、FTA 逻辑求解、最小割集或故障概率计算。本文对这些能力的约定属于后续开发要求。

自建知识默认可在本机检索，向外部模型发送需要当前设置允许使用自建知识；自建知识和正式案例库目前均不进入通用导出包。文档状态、发送范围和导出范围必须分开管理。

## 3. 先分清连接的对象

不能把“油斑”“某次油斑事件”“油斑可能由污染造成”和“某次检测支持污染解释”混成同一个节点。

| 对象 | 描述内容 | 示例 | 建议的组织方式 |
|---|---|---|---|
| 概念 | 可重复使用的工序、材料、结构、物性、缺陷、表现 | 萃取、残油、油斑 | 复用现有 `graph` 概念 |
| 文章 | 对知识的系统解释 | 萃取置换与残油 | MD 正文与文章目录 |
| 案例 | 一个有范围和版本的事件/项目 | LL-0001、SP-0001 | 案例主稿；未来案例目录 |
| 判断或假设 | 一个能够被检查的主张 | 本次异常可能与接触转移有关 | 案例内 H01 等编号；未来独立记录 |
| 证据 | 在特定条件下实际取得的观察 | 某项配对检查的脱敏结果 | 案例内 E01 等；与假设建立明确对应 |
| 检查方法 | 怎样区分几个解释 | 同位置异常/正常样的配对复测 | 方法文章或案例中的检查记录 |
| 控制点/措施 | 管住什么、怎样监测、异常时怎样响应 | 清洁状态、带液状态的监测与反应 | 现阶段写入关系字段与正文；未来可独立化 |
| FTA 事件与门 | 不利事件及其逻辑组合 | 顶事件 T01、AND 门 G01 | 单独的事件表和门表，不能用普通箭头替代 |

无需把正文的每个名词都建成节点。只有需要跨案例复用、参与检索或明确关联的对象才独立建模；其余保留为字段，避免出现大量没有分析价值的小节点。

## 4. 命名、编号与复用规则

### 4.1 优先复用已有对象

新增案例前搜索同义词和已有名称，检查“对象相同、定义相同、测试状态相同”后再复用。别名用于同一个概念的不同叫法，不用于把不同概念强行合并。

例如，残油和残溶剂不是同一对象；孔隙率、孔径分布与孔道连通性不是同一指标；热收缩、闭孔及高温完整性不能只用“耐热性”一个节点包办。测量方法和物性对象之间也要分开。

名称使用工程师能读懂的表述；ID 使用稳定标识。改显示名称不应随意换 ID。新旧对象确实不同则新建对象，并说明适用关系；不能覆盖旧 ID 使历史案例含义改变。

### 4.2 本规范的编号约定

| 对象 | 建议编号 | 当前是否被程序结构化识别 |
|---|---|---|
| 既有概念 | 沿用 `base_oilspot` 等 | 是，来自 graph；但不等于双链语法可直接使用 |
| 既有文章 | 沿用 `atlas_oil` 等 | 是，来自文章目录 |
| 既有机制边 | 沿用 `base_edge_027` 等 | 是，来自 graph |
| 案例 | `LL-0001`、`SP-0001`、`FTA-0001` | 否，目前是人工管理编号；作为唯一别名时可用于文章链接 |
| 案例内假设 | `H01` | 否；跨案例写为 `LL-0001:H01` |
| 案例内证据 | `E01`，FTA 建议用 `EVD01` | 否；跨案例加案例编号，避免同名混淆 |
| 案例组/证据组 | `CG-0001`、`EG-0001` | 否；用于今后识别同源事件与重复证据 |
| 新关系建议 | `REL-P-0001` | 否；P 表示候选，不是已经进入正式图谱 |

自建文章当前 ID 根据相对路径生成，不能仅在 MD 内写 `id: LL-0001` 就替换程序 ID。未来正式接入时，需建立稳定案例编号与当前文章 ID 的映射，并处理改名、移动、合并、停用后的引用。

## 5. 关系必须说明类型与方向

下面是人工登记与未来程序扩展共用的关系分类。除第 2 节列出的现有类型外，新增类型目前不具备专用解析和推理功能。

| 关系类型 | 方向 | 需要写明的内容 | 分析时允许怎样使用 |
|---|---|---|---|
| 解释 `explains` | 文章→概念/关系 | 解释哪部分、适用范围 | 提供原理背景 |
| 涉及 `about` | 案例→工序/物性/缺陷 | 在何种角色上涉及 | 召回相关案例，不能确认根因 |
| 条件影响 `affects_under` | 输入/状态→结构/响应 | 机制、中间过程、条件、验证方法 | 生成候选路径，检查本次是否满足条件 |
| 支持 `supports` | 证据→具体判断或关系 | 观察、方法、范围、限制 | 在匹配范围内提高该判断的证据支持程度 |
| 反对 `challenges` | 证据→具体判断或关系 | 与哪项预测不一致、检测能力 | 修正或收窄判断，不自动否定全部通用机理 |
| 验证 `tests` | 检查方法→判断/事件 | 阳性、阴性、不确定分别意味着什么 | 选择下一项有区分度的检查 |
| 针对 `addresses` | 措施→原因/传播条件 | 阻断位置、实施条件、复验 | 提出有依据的改善方向 |
| 控制 `controls` | 控制点→过程状态/关系 | 控制对象、监测、异常反应 | 生成控制计划修订建议，不自动发布标准 |
| 条件对应 `applies_under` | 关系/案例→适用条件 | 路线、结构、方法、工况等 | 匹配、条件未知或不适用；未知不能当匹配 |
| 同源 `same_evidence_group` | 案例/证据→证据组 | 共同事件或试验范围 | 去重，防止重复计数 |
| 冲突 `conflicts_with` | 判断↔判断 | 冲突内容、各自条件与证据 | 保留冲突并要求判别 |
| 版本替代 `supersedes` | 新版本→旧版本 | 为什么替代、何时生效、范围 | 当前检索用有效版本，历史仍可追溯 |
| FTA 输入/输出 | 输入事件→门→输出事件 | AND/OR、边界、逻辑解释 | 按明确定义处理逻辑，不能混为一般相关性 |

支持线指向一个可判断真伪或适用范围的主张。不要只写“E01 支持油斑”，因为“油斑”是概念，不是完整判断。

“证据支持通用机制”和“证据支持本次根因”需要两条分别受条件约束的判断。前者不能直接替代后者。

## 6. 一条可以用于分析的机制关系怎样写

### 6.1 内容顺序

1. **为什么有关。** 先写过程怎样传递：什么发生变化，材料、结构或检测状态怎样变化，再怎样表现为目标响应。
2. **由此要控制什么。** 写出相关工序、控制对象、观察/测量方法和异常反应原则。
3. **控制不好会怎样。** 区分可观察的直接后果、需要额外条件的下游后果，以及本案例已经观察到的后果。
4. **什么时候成立。** 写出必要条件、不能照搬的情况和关键未知项。
5. **怎样检验。** 说明应寻找的支持与反对证据，及能区分替代解释的检查。

页面可以保持“机理—控制点—失控问题”的阅读顺序；条件与证据作为分析必需信息保留，不需要重新增加用户已取消的“性能权衡”“证据边界”展示栏目。

### 6.2 机制要补齐中间过程

推荐主链：

```text
材料/过程输入或设备状态
  → 膜或涂层的中间结构/表面状态
  → 指定方法下的物性或可观察缺陷
  → 特定下游加工条件下的表现
  → 有证据支持的电芯影响
```

不是每个案例都要连到电芯。只知道基膜外观异常时，可以停在外观和待验证的结构变化；中间环节没有依据就标为候选，不能靠箭头补全事实。

不要把“孔隙率上升→所有传输性能改善”“拉伸倍率增大→某物性必然更好”写成无条件关系。关系方向、非单调情况和同时变化的结构因素应在机理及条件中说清楚。

### 6.3 条件表：匹配、未知、不匹配三种结果

| 条件维度 | 必须核对的内容 | 条件缺失时 |
|---|---|---|
| 材料及成孔路线 | PE 湿法、其他路线，材料功能类别 | 先问路线，不直接套用 |
| 层结构和加工状态 | 基膜/涂覆膜；陶瓷/聚合物；面别与层数；干湿状态 | 明确只作为候选参考 |
| 工序和取样位置 | 形成位置、发现位置、取样与检测坐标对应 | 先解决物料同源性 |
| 测量定义 | 方法、单位、方向、受力/温湿等关键条件 | 不能把不同量值当同一响应 |
| 设备与作用方式 | 只保留必要通用特征，不保留识别性编号 | 不能假定每条线作用方式相同 |
| 时间和有效版本 | 变更前后、措施先后、知识是否仍适用 | 保留版本不确定性 |
| 适用边界 | 哪些条件外未验证或已有反例 | 不外推，列出再验证条件 |

建议对未知条件输出具体问题，而不是给一个看似精确的“适用度百分比”。条件匹配也只是允许使用这条候选关系，不等于原因已经成立。

### 6.4 关系登记表模板

```markdown
### REL-P-编号｜关系的清楚名称

- 关系状态：候选/已审核纳入/需复核/停用；当前是人工记录。
- 源对象：类型、ID、名称；不存在则写建议新增。
- 目标对象：类型、ID、名称。
- 关系类型与方向：
- 要表达的具体判断：

#### 为什么有关
完整解释过程，明确中间结构或状态，不仅写“存在影响”。

#### 质量控制点
控制对象、对应工序、检查/监测方式、异常反应原则。

#### 控制不当可能导致的问题
直接后果；下游后果所需额外条件；本案例实际观察到哪一层。

#### 成立条件、未知项和不适用情况
按材料、层结构、工序、测法、工况、时间版本列出。

#### 证据与替代解释
支持证据号、反对证据号、同源组、证据核验状态；未取得的证据不要列入已取得栏。
哪些现象也可以由其他机制造成；现在仍不能排除什么。

#### 下一项判别检查
做什么、为什么有区分度、需要什么对照、结果A/B/不确定分别如何处理。

#### 对应知识与审核
文章 ID、案例编号、已有关系 ID、建议更新内容、审核角色与知识稿日期。
```

## 7. 复用现有图谱字段，避免正文与连线脱节

当前 `graph` 中节点字段为 `id`、`label`、`type`、`stage`、`summary`、`article_ids`。机制边的核心字段如下：

| 字段 | 填写要求 |
|---|---|
| `id` | 全局唯一、稳定；修改内容不随意改变 ID |
| `source` / `target` | 已存在的概念 ID；方向符合关系语义 |
| `relation` | 简洁说明怎样相关，不能只有“影响” |
| `mechanism` | 通顺解释中间过程和关系成立原因 |
| `control_points` | 由机理导出的控制点，数组中的每项可读、可观察 |
| `failure_modes` | 控制不当的直接问题及有条件下游问题 |
| `conditions` | 关键前提与适用限制，不能全部写成“视情况而定” |
| `checks` | 能检查该关系的具体方法和比较路径 |
| `article_ids` | 已加载的正式知识文章 ID，提供完整解释 |

当前概念节点的 `article_ids` 第一项用于进入相关完整知识。应把最贴近节点的解释文章放在首位，不要把某个单次案例随意置顶替代原理文章。

既有关系示例：`base_edge_027` 连接 `base_extract`（萃取）与 `base_oil_residue`（残油）。它关联文章 `atlas_extraction` 与 `base_extraction_drying`。新的经验卡若对此提供支持或反例，先登记“案例证据→该关系或更窄的案例判断”，而不是复制一条相同的萃取→残油关系。

可以阅读当前对应正文：[萃取置换与残油](../知识图谱/06_萃取置换与残油.md)、[油斑、CCD与污染路径](../知识图谱/12_油斑、CCD与污染路径.md)。这些链接指向本项目通用知识，不是公司原始材料。

关系修改需要同步三处含义：图谱结构、相关 MD 解释、分析剧本或检查规则。当前通用校验工具会检查 ID、端点、文章关联及必要字段；它不会替人证明机制正确，也不能理解全部正文矛盾。不要只依赖“校验通过”。

**不要直接向 `graph/` 放入仅含案例或 FTA 的新 JSON 并期待自动生效。** 当前加载器按普通 `nodes`/`edges` 读取，会把不同语义混在一起或忽略其他结构。新增结构应先扩展明确的加载规则、验证规则和显示方式。

## 8. 从一个案例建立关系的实际步骤

### 8.1 先做对象清单

从 MD 中提取工序、结构、物性、缺陷、检测方法、下游表现、候选原因和证据。先映射已有节点，不存在的填“建议新增”。不要为每个案例重复创建“萃取”“油斑”“涂布”等概念。

### 8.2 先连主题，再登记判断

当前可在投递副本中使用以下真实已有目标：

```text
相关知识：[[油斑]]、[[残油]]、[[atlas_oil]]、[[atlas_extraction]]
```

这些链接便于找到相关内容，但只说明主题关联。要让案例参与原因分析，还必须在正文按第 6 节记录具体判断、条件、证据与检查。

### 8.3 区分五种对图谱的贡献

1. 解释已有关系：用更易懂的表述说明原理，不改变技术范围。
2. 增加适用条件：说明何种材料、位置、检测状态下才成立。
3. 提供案例支持或反对：登记证据组与范围，不把次数当概率。
4. 补充判别检查：说明哪项观察能区分两个相似机制。
5. 提出新关系或修正旧关系：保留修改前后内容、原因和审核状态。

### 8.4 每条关系单独判断，而不是整篇整体背书

一个专项可能可靠地证明“某组合措施降低了某类外观异常”，但没有证明“组合中的某一个参数独立起决定作用”。前一个判断可以保留条件内支持，后一个仍应待验证。

一个反例可能说明旧关系条件写得过宽，未必说明机理完全错误。先核对路线、测法、位置和版本，再决定补条件、拆关系、标冲突或停用。

## 9. 用 CCD 油斑说明五类知识怎样协作

以下仅为编制和分析流程示例，没有使用公司案例原始数据，不代表已确认任何现场根因。

### 9.1 输入只允许说明到已有事实

若已知信息仅为“CCD 报告油斑，影响 A 品率”，最多可记录检测系统给出了某类缺陷标签及用户描述的业务影响。仍要核对实物是否对应、判级及统计口径、标签含义。不能先写“残油超标导致降级”。

### 9.2 先调取哪些知识

| 知识层 | 调取内容 | 作用 |
|---|---|---|
| 初始知识 | 外观检测与取样对应、萃取和残留的基础解释 | 防止把图像标签当成分鉴定 |
| 图谱 | 油斑、残油、萃取、可能的污染路径及适用条件 | 建立需要检查的候选关系 |
| 经验教训 | 实物对应、首次出现位置、周期和面别的排查经验 | 优先选择有区分度的问题 |
| 优秀专项 | 经记录核查的判别试验及改善验证方法 | 参考如何设计验证，而不是照搬措施 |
| 客诉 FTA | 仅在顶事件及产品/工况匹配时参考相关分支 | 检查下游失效路径，避免强行引入不相关客诉 |

### 9.3 下一问题由缺口决定

| 关键问题 | 为什么问 | 不同结果的作用 |
|---|---|---|
| CCD 位置是否能在实物上重复对应？ | 区分实物异常与检测/对应问题 | 对应失败时先核对定位、成像和识别，不能直接调工艺 |
| 异常实物的形貌和物质状态是什么？ | 区分不同外观形成机制 | 成分未确认则维持多个假设 |
| 沿工序同源追溯，首次在哪一段出现？ | 缩小形成范围 | 注意物料滞后，不能只比较同时刻 |
| 横向位置、纵向周期、面别是否稳定？ | 帮助区分固定作用位置与随机来源 | 分布是定位线索，不是设备根因证明 |
| 是否有能够区分候选机制的配对检查？ | 用证据改变判断 | 结果阴性仍需核对方法覆盖和检出能力 |

### 9.4 有证据后怎样反写知识

保留本次真实观察的脱敏摘要，更新相应假设状态；把可复用检查写入经验卡。只有当通用关系确需增加条件或修改解释时，才提出图谱变更。不能因为一次对话“看起来合理”，就把候选原因作为正式知识回灌。

## 10. FTA 与图谱的连接规则

### 10.1 两类结构各有职责

图谱说明概念间的机制与条件；FTA 说明一个明确顶事件可以通过哪些事件组合发生。多条普通箭头无法表达这些输入究竟要同时发生还是任意发生。

FTA 的 AND/OR 逻辑与共同依赖需要单独建模；重复出现的同一个事件不能在量化时当作独立事件。方法参考 [NASA《Fault Tree Handbook with Aerospace Applications》](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)第 4—6 章；本文中的具体字段和隔膜案例整理流程为本项目设计约定。

### 10.2 事件与概念分开

“残油”是概念；“在指定对象、方法和条件下残油达到某不利状态”才是事件定义。FTA 事件可以映射到“残油”概念获取原理，但不能把概念节点当作已经发生的事件。

每个事件需要：事件 ID、可判定描述、对象和边界、类型、验证状态、关联概念、证据与检查。阈值若属于内部受控内容不进入通用稿；由此无法独立判断时明确标注。

每个门需要：门 ID、类型、输入事件、输出事件、逻辑解释、假定条件及未覆盖路径。未知门逻辑明确为待复核，不由模型随意补成 OR。

### 10.3 与门、或门和待查清单要分开

待查原因清单只表示“可能存在这些解释”，不自动保证它们足以或完整地解释输出事件。因此，原报告只有人机料法环清单时，先保留待查结构，不机械转换成正式 OR 门。

资料中的“发生”“未拦截”“管理缺口”也不自动构成并列 OR 分支。先定义顶事件：若关注客户收到不合格品，与只关注膜面缺陷形成，树的边界和逻辑会不同。不能默认客户现象已证明供应方责任或漏检。

### 10.4 后续结构示例：纯逻辑演示，不是隔膜失效结论

以下 JSON 是**未来独立 FTA 加载器的设计示例**，当前不能直接放进 `graph/` 使用。

```json
{
  "schema_version": "fta-draft-1",
  "case_id": "FTA-DEMO-0001",
  "status": "synthetic_example",
  "scope": "纯逻辑演示，不代表真实失效机制",
  "top_event_id": "T01",
  "events": [
    {"id": "T01", "label": "演示顶事件", "type": "top"},
    {"id": "M01", "label": "路径甲成立", "type": "intermediate"},
    {"id": "M02", "label": "路径乙成立", "type": "intermediate"},
    {"id": "B01", "label": "两路径共享的事件A", "type": "basic"},
    {"id": "B02", "label": "事件B", "type": "basic"},
    {"id": "B03", "label": "事件C", "type": "basic"}
  ],
  "gates": [
    {"id": "G01", "type": "OR", "inputs": ["M01", "M02"], "output": "T01"},
    {"id": "G02", "type": "AND", "inputs": ["B01", "B02"], "output": "M01"},
    {"id": "G03", "type": "AND", "inputs": ["B01", "B03"], "output": "M02"}
  ]
}
```

这份示例表达 `(A 且 B) 或 (A 且 C)`。B01 在两条路径中复用同一个 ID，不能复制成两个互相独立的事件。它只是一个结构示例；正式记录还必须补全各事件的条件、证据、核验状态、概念映射与分支覆盖情况。

### 10.5 分支状态不能只用“红/绿”表示

至少区分：待验证、条件内支持、条件内不支持、证据冲突、未展开。支持和反对必须附范围；一次未检出不自动删分支。未展开事件不应冒充已经追到根因的基本事件。

同一节点的“模型里是否成立”与“现场是否已有证据”是两个问题。逻辑结构正确不等于事件已发生，树画得完整也不等于排查已经完成。

不具备事件数据、观察范围、依赖关系及方法前提时，只做定性分析。不能根据文章数量、相似度或连线数量生成故障概率、贡献率或根因百分比。

## 11. 后续案例关联登记结构

本节是程序扩展约定，现阶段可先在 MD 中以表格记录。不要把这些字段误认为现有 frontmatter 已支持。

### 11.1 推荐的独立记录

| 记录 | 最低字段 |
|---|---|
| 案例目录 | `case_id`、类别、标题、相对路径、版本、文档状态、适用条件、有效状态、发送/导出范围 |
| 案例判断 | `claim_id`、`case_id`、明确主张、涉及对象、条件、技术状态、未知项 |
| 证据记录 | `evidence_id`、`case_id`、证据组、脱敏观察、方法、样本范围、对照、限制、核验状态 |
| 关系登记 | `relation_id`、源/目标类型与 ID、关系类型、具体表述、条件、状态、证据引用、版本 |
| FTA 记录 | 顶事件、系统范围、事件集合、门集合、事件映射、证据关联、版本 |
| 变更记录 | 修改对象、修改前后摘要、原因、审核状态、受影响案例与评测 |

发送和导出范围不得从“已审核”自动推导。内容审阅通过、可以在本机使用、可以发给某个模型服务、可以发布到 GitHub，是不同范围；默认不增加外发权限。

### 11.2 支持关系示例

以下是字段填写示意，全部使用演示编号，没有真实案例证据。状态保持待核验；不能仅凭示例把关系升级为有效。

```json
{
  "schema_version": "case-link-draft-1",
  "relation_id": "REL-DEMO-0001",
  "source": {"type": "evidence", "id": "LL-DEMO-0001:E01"},
  "target": {"type": "claim", "id": "LL-DEMO-0001:H01"},
  "relation_type": "supports",
  "statement": "待填：哪项实际观察支持了H01的哪部分预测",
  "conditions": ["待填适用材料、位置、测法与范围"],
  "status": "pending_review",
  "evidence_group_id": "EG-DEMO-0001",
  "related_graph_edge_ids": ["base_edge_027"],
  "related_article_ids": ["atlas_extraction"],
  "limitations": ["这是字段示例，没有提供真实观测，不能参与现场判断"]
}
```

当前没有完整案例注册表和证据解析器，以上对象不会被现有程序自动创建。将来接入时必须拒绝找不到目标的有效关系；待补目标可留在候选区，不混入正式图谱。

### 11.3 一份记录只维护一个权威版本

机制正文与图谱关系应由明确登记关系关联，减少同一句机理在多处各自演变。案例证据记录保持唯一，文章中引用匿名标识与摘要；同一事件拆成几篇也使用同一证据组。

未来加载器至少要校验：ID 唯一、路径不越界、目标存在、关系类型与对象类型兼容、版本有效、条件非空、演示记录不进入生产检索。停止使用的内容保留历史，但不默认进入当前分析材料。

## 12. 智能体怎样使用这张网络

以下是分析行为要求；其中结构化条件筛选、证据图和 FTA 运算需要后续实现，不能声称当前已全部具备。

### 12.1 先确认对象，再找相似案例

先确定问题对象、材料/层结构、工序、检测方法、当前已知事实和缺失项。若路线或测量定义不同，即使缺陷名称相同，也不能优先套用历史原因。

### 12.2 取出一张与本次问题有关的小图

从现象和指标节点出发，选取直接相关的机制关系及其必要中间节点，再取适用案例、反例和验证方法。可以逐轮扩展；不必把全部五类知识一次性塞进上下文，也不为凑齐类别召回不相关 FTA。

### 12.3 为每个候选保留完整判别信息

至少包含：机制、成立条件、本次已有支持、本次已有反对、未知条件、相似案例能借鉴什么、不能照搬什么、下一项能区分它的检查。历史案例的事实不能进入“本次已知事实”栏。

### 12.4 选择下一问

优先级考虑：是否能明显区分候选、是否是关键前提、所需证据能否取得、检查成本及潜在影响。优先级不是发生概率。每次问当前最关键的一项，并解释回答不同会怎样改变排查方向。

不要重复询问已经回答且未被修正的问题。回答未知就记录未知，并给出取得证据的方法；不能把没有反对意见当作确认。

### 12.5 更新当前分析，不能自动改写正式知识

用户给出新检查结果后，更新本轮事实、假设状态和下一项验证。生成阶段性结论时说明能确认什么、不能确认什么、下一步依赖什么证据。

“整理成经验卡”可以生成待审核草稿；“纳入正式图谱”仍需要明确的关系审查和发布流程。模型答案、网络摘录以及自动归纳内容都不是自证证据。

### 12.6 给模型的最小分析材料

建议后续每轮材料由以下内容组成：

1. 当前问题与用户实际提供的事实，含未知和修正记录。
2. 相关概念定义，尤其容易混淆的测量和状态。
3. 少量匹配的机制关系：机理、条件、控制点、失控问题、检查。
4. 必要的历史案例摘要、反例及各自适用范围。
5. 如涉及客诉：相关 FTA 分支、门逻辑和验证状态。
6. 明确的下一问/阶段性结论规则。

若上下文不足，宁可减少候选数量，也不要删除留下来的候选的关键条件和证据状态。资料可追溯不意味着向用户展示公司原文件名或内部记录。

## 13. 星球中的连线和亮起怎样解释

- 当前亮起应解释为实际进入本次分析材料的文章、概念或关系，不是模型内部注意力，也不是根因已经确认。
- 用户点击、搜索选中和本轮使用是不同状态，界面应有不同反馈，避免都叫“分析依据”。
- 案例主题线与有条件机制线需要可辨识；FTA 门和证据线将来接入时也要保留类型，不把所有线画成同一种因果箭头。
- 被检索到但因范围不匹配或上下文限制未使用的内容，不应冒充本轮实际依据。
- 外部搜索得到的资料仍是待核验候选。流星动画代表实际获取并纳入本轮的外部资料，不代表已经进入正式知识库。
- 新增案例节点后，点击应能看到摘要、适用条件、结论状态和关联知识；不展示原报告路径、客户标识或原始数据。

这些是界面含义与后续实现要求；仅新增 MD 规范不会增加星球动画、证据节点或 FTA 计算功能。

## 14. 关系审核、冲突处理与版本维护

### 14.1 每次新增先回答六个问题

1. 两端对象是否已经存在，是否被重复创建或混淆？
2. 关系究竟是主题关联、机制解释、证据支持还是 FTA 逻辑？
3. 机制是否通顺，是否跳过了决定性的中间过程？
4. 条件是否足够区分能用与不能用的场景？
5. 证据是实际取得、报告转述还是仅为预期，是否与已有证据同源？
6. 这条关系将怎样改变下一问、验证计划或结论？若完全不改变，是否只需保留正文？

### 14.2 冲突处理顺序

先检查定义和单位，再查材料/路线/测法/位置/版本是否一致，然后核对证据方法与样本。条件不同则拆分或补条件；条件相同而结果相反则标记冲突，列出能判别的下一项检查。

不得通过删除反证使知识表面一致，也不能因为新报告日期较晚就自动覆盖所有旧结论。无法解决的冲突应进入分析材料，并提示模型保持不确定性。

### 14.3 失效与复审触发条件

材料或层结构改变、设备作用方式改变、检测方法或判级口径改变、控制窗口变更、出现复发或反例、发现源报告证据有误，都应触发复审。记录受影响关系、案例、剧本和待验证事项。

停用一个对象前检查入边和出边。合并时保留旧 ID 的迁移说明；不要产生指向已删除对象的连线。正式案例未来接入后，应把这类检查自动化。

## 15. 现在怎样操作，后续怎样接入

### 15.1 当前可以直接执行

1. 在正式案例库保存脱敏的 MD 主稿，使用配套三类模板。
2. 在正文中写关系登记表，列真实节点/文章/关系 ID，以及候选新增项。
3. 需要当前程序试用时，制作知识投递副本；设置唯一标题和别名，使用支持的双链目标。
4. 同步知识，核对文章是否出现、链接是否连到正确对象，使用自然问法检索。
5. 在允许使用自建知识的模型材料中核对实际纳入内容；不要只凭星球多了一个节点判断已可用于模型分析。

目前普通投递副本均标为“未审核”。若要改变机制图谱，需要另行审查并修改 `graph` 与相应正式正文；复制案例文件不会自动完成此事。

### 15.2 建议的后续实现顺序

| 顺序 | 实现内容 | 验收重点 |
|---|---|---|
| 第一阶段 | 正式案例主稿加载与独立目录、稳定 ID、类别和版本 | 原始文件仍不扫描；主稿只加载一次；模型/导出范围明确 |
| 第二阶段 | 案例与概念、文章、关系的类型化连接 | 链接无歧义，主题与机制分开，断链可检查 |
| 第三阶段 | 判断—证据—检查记录与条件匹配 | 未知不当匹配，同源不重复，冲突不隐藏 |
| 第四阶段 | FTA 事件、门、映射与定性检查 | 门输入输出完整、事件复用、树结构与现场状态分离 |
| 第五阶段 | 以案例和证据驱动的追问与回归评价 | 新知识确实改变合适的问题，不造成越界归因 |

每阶段完成后再宣称对应能力上线。文件中的规划字段不能替代实现和验证。

## 16. 验收用的问题集

这些是人工核对与后续回归题的建议，不是真实生产事件。

| 场景 | 应有行为 | 不应出现 |
|---|---|---|
| 只说 CCD 检出油斑 | 询问实物对应及相关条件，保留成分未知 | 直接确认残油超标 |
| 找到同名缺陷，但路线不同 | 说明适用条件不匹配或未知 | 因标题相似照搬措施 |
| 两篇案例来自同一专项试验 | 标出同源证据 | 说“两次独立验证” |
| 清洁、换料、调整检测同时进行后改善 | 只支持组合效果，识别混杂 | 指定其中一个动作是唯一根因 |
| 一个检测未发现异常 | 说明方法覆盖与未检出限制 | 把全部分支永久排除 |
| 正文里有 `[[油斑]]` | 建立主题关联 | 自动新增油斑与电芯失效的因果边 |
| FTA 缺少门逻辑 | 请求澄清或标待复核 | 自动补成 OR 并给出概率 |
| 用户修改先前回答 | 更新事实与相应候选 | 延用已被纠正的结论 |
| 案例改名、移动或停用 | 检查引用和运行时 ID 影响 | 旧链接悄然失效却宣称知识完整 |
| 外部文章提出新机制 | 标为待核验候选，说明条件 | 搜索后自动成为正式知识 |

## 17. 每条关系的最终检查清单

- [ ] 对象类型、名称和稳定标识明确，没有以文件名代替技术对象。
- [ ] 现有对象已优先复用，新对象有独立必要性，别名不冲突。
- [ ] 连线类型和方向准确，主题线没有冒充因果线。
- [ ] 机制解释了中间过程，工程师不依赖模型也能读懂。
- [ ] 质量控制点来自该机制，失控问题没有无依据地跳到下游后果。
- [ ] 适用、不适用与未知条件分开，测量和物料位置可比较。
- [ ] 支持、反对、预期和缺失证据清楚区分，同源证据已去重。
- [ ] 有至少一项能够改变候选排序的判别检查；无信息价值的连线不过度扩张。
- [ ] FTA 事件与门单独记录，普通图谱不能代替逻辑定义。
- [ ] 正文、结构字段和分析规则的含义一致，版本与停用状态可追溯。
- [ ] 当前支持与后续规划已区分，没有把新增文档称为已上线功能。
- [ ] 未引入原始公司文件引用、身份信息、原始数据或未经允许的外发范围。

知识增长应体现为更清楚的机制、更准确的适用范围、更有效的判别检查和更可靠的结论状态，而不仅是文章、节点和连线数量增加。
