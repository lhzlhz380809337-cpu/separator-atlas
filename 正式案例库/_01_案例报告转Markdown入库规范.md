# 案例报告转 Markdown 入库规范

版本：1.0｜编制日期：2026-10-11｜适用对象：湿法 PE 基膜、陶瓷及聚合物涂覆、相关电芯加工与失效分析。

本文件说明怎样把现场经验教训、优秀专项、客诉 FTA 报告，整理成工程师能够学习、模型能够检索、图谱能够关联的知识。配套阅读：[五类知识关联与图谱维护规范](./_02_五类知识关联与图谱维护规范.md)。

**目标是保存可复用的分析过程和有条件的结论，不是把报告逐页转成文字，也不是把原报告中的结论全部认定为事实。** 报告排版不佳可以重新组织；报告缺少的实验、数据和验证过程不能补写成已经发生。

## 1. 先了解当前程序能做什么

| 内容 | 当前行为 | 整理时怎么做 |
|---|---|---|
| 本文件夹“正式案例库” | 尚未接入自动加载、知识检索及通用导出 | 先在这里保存规范和案例主稿；放入文件不等于程序已经学会 |
| “知识投递”中的 MD/TXT | 扫描正文并参与本地检索，形成文章节点 | 当前需要试用案例时，将整理好的可投递副本放入对应子目录 |
| 自建文章的 `[[名称]]` 链接 | 匹配既有概念名称、文章标题、文章 ID 或别名后连线 | 表示主题关联，不能自动升级为因果关系 |
| 自建文章审核状态 | 统一标记为用户添加、未经过专业审核 | 在正文中记录真实审核情况；正文写“已审核”不会改变程序状态 |
| 案例专属字段、FTA 结构 | 目前不会作为结构化记录解析 | 先用本规范保存；后续增加加载器和校验后再接入 |

自建案例默认仅参加本地检索；外部模型使用还需要设置允许发送自建知识，并核对内容的发送范围。文件写成“已审核”或保存进正式案例库，不会自动改变发送权限。当前自建知识和正式案例库均不进入通用导出包。

这两份规范文件名以 `_` 开头，是维护说明，不是生产案例；即使复制进“知识投递”，当前扫描规则也会跳过。不要为了增加知识数量，把规范、空模板或演示案例当成真实经验入库。

## 2. 五类知识各自负责什么

| 类别 | 核心用途 | 转换时的要求 |
|---|---|---|
| 初始知识 | 解释术语、工序、材料、测量和基础机理 | 案例引用已经存在的知识；发现缺项时提出补充，不重复堆放同一原理 |
| 知识图谱 | 连接工序、结构、物性、缺陷、下游表现和控制点 | 从案例中提炼候选关系，保留条件、证据状态和适用范围 |
| 现场经验教训卡 | 说明遇到相似问题先查什么、哪些措施有效或无效 | 保留关键现象、排查分支、误判和可执行的检查 |
| 优秀专项 | 保存复杂问题从定义到验证、改善和维持的完整方法 | 判断测量、对照和验证是否支持结论，不能只摘录改善效果 |
| 客诉 FTA | 从清楚定义的失效事件逐层梳理可能路径 | 保留事件定义、逻辑门、分支状态及判别证据，不能只保存树形截图 |

这五类是知识用途分类，不是可信度排名。“优秀”“结案”“客户认可”都不能替代具体技术结论的验证。

## 3. 文件组织、命名与主稿管理

建议今后逐步采用以下目录；本规范不代表这些子目录或自动化流程已经创建。

```text
正式案例库/
  _01_案例报告转Markdown入库规范.md
  _02_五类知识关联与图谱维护规范.md
  现场经验教训/     ← 已整理的唯一主稿
  优秀专项/
  客诉FTA/
  _待整理/          ← 草稿；不得自动当作可用知识
  _已停用/          ← 留存版本，不参加正常分析

知识投递/
  现场经验教训/     ← 当前版本需要检索时使用的投递副本
  优秀专项/
  客诉FTA/
```

- 一篇经验卡聚焦一个可复用问题或一条完整教训。一份报告有多个独立问题时拆篇，用共同案例组号关联。
- 一个专项可以保留一篇总稿，再拆出方法或经验卡；拆出的文章不是新的独立证据。
- 一个 FTA 主稿对应一个明确顶事件及一组明确边界。多个性质不同的顶事件应分开建树。
- 建议编号：`LL-0001` 为经验卡，`SP-0001` 为专项，`FTA-0001` 为客诉树。编号是本知识库新建标识，不沿用公司报告号、客户代码或生产批号。
- 文件名示例：`LL-0001_CCD外观异常的实物对应检查.md`。主题名称描述现象和学习点，不提前宣布未经验证的根因。
- 主稿只有一份。投递副本与主稿使用同一案例编号及内容版本；修改主稿后再更新副本，不在两个位置各自改写。
- 当前自建文章 ID 根据文件相对路径生成，改名或移动会改变程序 ID。首次投递后尽量固定路径，改动前检查其他文章的引用。
- 停用时同时把投递副本移出“知识投递”，或将其文件名/所属目录改为 `_` 开头，再同步知识；仅在正文写“停用”不会停止检索。不要通过整目录同步，把原始报告一并复制进知识投递。

## 4. 处理一份报告的标准流程

### 第一步：先识别对象和资料范围

确认材料路线、产品层结构、工序、检测状态、问题现象、时间顺序及报告版本。资料没有说明的内容标为“未知”。两份不同产品、不同时间或不同路线的 CP、报告和检测结果，不能拼接成同一个连续过程。

先列“资料覆盖了什么、缺少什么”，再开始总结。尤其检查附件是否缺失、图表坐标是否可读、结论是否只有口述、引用的试验是否真的有记录。扫描件经过 OCR 后，人工核对小数点、单位、正负号、MD/TD、样本对应关系和逻辑门。

### 第二步：提取事实，暂时不要写根因

把信息分别放进四个框：

1. 报告实际记录的观察、测量或试验结果。
2. 报告作者的解释、猜测或结论。
3. 整理者为帮助理解补充的通用机理。
4. 尚未提供的信息和待验证问题。

“报告记录过”仍不等于整理者已复核原始记录。需要分别写明记录来源层级和核验状态，不能把第二、三类改写成第一类。

### 第三步：建立事件时间线和物料位置关系

按“异常前—首次发现—排查—临时处置—改善—复验—维持”整理。记录相对工序与物料滞后，避免把同一时钟时刻的上游工况和下游检测误认为同一段膜。共享知识用相对时间和通用位置表达，不保留可识别日期、卷号和设备编号。

### 第四步：拆解原结论的证据链

对每个主要判断追问：观察到了什么？测法是否适用？正常对照是否可比？还有什么能产生同样现象？有没有做能够区分这些解释的检查？措施有效是否可能由同期其他变化造成？

如果报告只写“清洁后恢复”，结论可以是“清洁措施与恢复同时出现”，不能直接补成“已证明某辊面污染是唯一根因”。

### 第五步：转换为通用、去标识的知识表达

保存机理、诊断逻辑、方法和适用条件；删除识别性信息及原始数值。脱敏不能改变技术含义，无法兼顾时将该细节留在公司受控记录中，在知识稿中说明由此带来的结论限制。

### 第六步：按类别填入模板

使用本文件第 11—13 节的模板。每条重要结论就近写出条件、证据状态和限制，不把所有限制只放在文章末尾。

### 第七步：建立知识关系

先找已经存在的概念节点和文章，再提出新增关系。至少说明本案例解释了什么知识点、支持或反对哪一条关系、能指导哪项检查。具体字段与规则见配套规范。

### 第八步：审核并投递

分别检查技术内容、信息暴露、关联准确性、文件格式。可以先保存为待核验案例；不完整并不等于没有价值，但必须让模型看得出哪些部分不能用于确认根因。

## 5. 信息保留与脱敏规则

本案例库延续项目既定要求：**不展示公司原始文件名、来源路径、客户或产品标识、原始检测数据、配方和具体生产设定窗口。** 匿名证据号用于表达论证关系，不是对内部文件的公开引用。

| 原材料中的内容 | 在知识稿中的处理 |
|---|---|
| 客户名、产品牌号、人员、供应商、线体和设备编号 | 改成与分析相关的通用类别；无必要则删除 |
| 原文件名、内部链接、截图水印、页眉页脚、二维码 | 不进入正文、标题、链接、图片说明、附件名或元信息 |
| 真实参数、配方、检测原值、良率、收益 | 不复制；在有依据时概括趋势和判别结果，说明数值未纳入知识稿 |
| 图表与照片 | 默认转写为脱敏文字结论和方法说明；确需展示时另做专门处理，不直接嵌入原截图 |
| 精确日期、批次、卷段等组合 | 用相对时间、异常区/邻近正常区、同源配对等表达，保留诊断意义 |
| 试验条件和测量口径 | 保留可公开的材料类型、方法类别、方向及状态；敏感细节缺失影响可比性时明确说明 |
| 内部证据追溯 | 如现场需要，在公司受控系统另建映射；不把映射表、受限链接或原始路径放进本案例库 |

不能用“换个名字”代替完整脱敏；也不能通过归一化、百分比、重新绘图把可识别原始数据间接带出。不允许把缺失值改成“典型值”，或为了让报告完整而编造试验结果。

数字删除后若无法支撑原报告的统计结论，应降级表达。例如写“报告描述改善，但本知识稿不含足以复算的样本信息，因此不能独立判断改善幅度和统计可靠性”。

## 6. 案例至少要交代的工程条件

| 条件组 | 最低需要交代的内容 |
|---|---|
| 材料与路线 | 湿法 PE 或其他路线；基膜/中间体/涂覆膜；陶瓷或聚合物；单面或双面、单层或复合层；未知项 |
| 工序位置 | 缺陷首次发现位置、推定首次形成位置、其间经过的工序；不要将两者混同 |
| 现象定义 | 观察对象、缺陷形态、指标方向、发生范围和判定方法；避免只写“变差” |
| 空间分布 | MD/TD、膜面/背面、边/中、固定横向位置、纵向周期或随机；取样与 CCD 坐标对应方式 |
| 检测状态 | 在线/离线、干态/浸液态、温湿及受力条件、制样与测试方法；缺失条件对解释的影响 |
| 对照与变更 | 正常对照与异常样的可比性；原料、设备、工艺、检测及判级规则的同期变化 |
| 时间与版本 | 适用设备/路线的通用版本、相对事件顺序、知识稿版本、最后复核日期；知识稿日期不冒充生产日期 |

若指标是 Gurley 时间，要写明时间变长对应何种测试意义，不能写含混的“透气性上升”。涉及力学或热收缩时说明方向及测试条件；涉及粘接时说明界面对象和测试状态。不要将油斑外观直接等同于白油成分，也不要将 CCD 检出增加直接等同于实物缺陷增加。

## 7. 事实、证据、判断与状态怎么写

### 7.1 使用四套相互独立的状态

| 维度 | 推荐状态 | 说明 |
|---|---|---|
| 文档流程 | 草稿、待审核、已审核、待更新、停用 | 说明文件管理状态，不证明内容正确 |
| 单条技术判断 | 待验证、条件内支持、条件内不支持、存在冲突、信息不足 | 同一案例里各条判断可以不同 |
| 证据核验 | 报告转述、记录已复核、方法与样本已核查、不能复核 | 说明实际核验到了哪里 |
| 改善验证 | 未实施、已实施待复验、短期有效、规定范围内持续验证、复发或失效 | 不以动作完成替代效果验证 |

“已结案”是原报告的流程状态，可以记录为转述；不是单条因果关系的验证状态。不要为了统一文章标签，把尚有争议的分支全部标成已验证。

### 7.2 证据记录的最低字段

| 证据号 | 可公开的观察摘要 | 方法、对象和位置范围 | 支持/反对哪个判断 | 其他解释或限制 | 核验状态 |
|---|---|---|---|---|---|
| E01 | 仅填实际取得并有记录的观察 | 说明配对、方向、位置和方法适用性 | 对应 H01、关系号或 FTA 事件号 | 如同期多措施、样本代表性不足 | 不省略 |

- E01 只在本案例内唯一；跨案例使用 `LL-0001:E01` 这样的组合标识。
- “应该看到什么”属于验证计划，不属于已取得证据。
- 尚未取得的证据列入“待验证计划”，不填入已取得证据表，也不计入支持链。空模板中的 E01 占位行在实际使用时应填写有效记录或删除。
- “未检出”要说明方法覆盖、检出能力、取样位置和范围；不能自动改写为“不存在”。
- 同一批试验被专项、经验卡和客诉总结重复引用，只算同一证据组，不当作三次独立验证。
- 公开研究能够支持通用机理，但不能证明当前案例中该机制实际发生。

### 7.3 可接受的结论写法

推荐结构：**在什么条件下，根据哪些已取得证据，支持什么判断；哪些替代解释已经检查，哪些还没有；结论最多适用到哪里。**

不推荐：“拉伸取向及后续保持或松弛决定可回复变形。”

推荐：“拉伸会使部分分子链沿受力方向排列。后续加热和约束条件会影响这些结构在受热时是否回缩，因此不能只看拉伸倍率判断最终热收缩；还需结合热定型条件和同方法下的 MD/TD 热收缩测试。”这是机制写法示例，不能替代具体产品验证。

## 8. 把结论写成可以检索的片段

当前程序按 Markdown 标题与段落切分正文，并不会每次把整篇文章全部交给模型。因此：

- 一个小节聚焦一个判断、机制或检查任务，采用“萃取后异常区与正常区如何配对检查”这类明确标题。
- 每个关键小节重复必要的对象、条件、状态；不要只写“由上述可知”“参见前文”。
- 建议每个知识小节约 200—600 个汉字；这是写作建议，不是强制格式或检索保证。
- 大表拆成若干小表，机理、条件和判定不要相隔几十行；检查结果与假设影响写在同一行或相邻段落。
- 最前面写一段短摘要，包含现象、适用对象、最有用的检查和结论状态，便于阅读；当前程序自动摘要仍受自身提取方式影响。
- 不把整篇资料放进代码块；正文用一至四级标题。代码块只用于模板、示例数据和确有必要的结构表达。
- 一篇文章只用一个主标题。使用 UTF-8 编码，优先 `.md`。

## 9. 当前可用的顶部元信息

投递副本可使用以下格式。尖括号内容需要替换；此处只是模板，不是实际案例。

```yaml
---
title: LL-0001｜CCD外观异常的实物对应检查
stage: 基膜
tags: 经验教训, 油斑, CCD, 实物对应
aliases: LL-0001
links: 油斑, atlas_oil
---
```

当前仅识别 `title`、`stage`、`tags`、`aliases`、`links` 这五个字段，且是简单的单行文本解析，不是完整 YAML 解析器。`stage` 只支持“基膜、涂覆、电芯、方法”。跨工序适用范围写在正文中，不要将 `stage` 填成“基膜/涂覆”。

`tags`、`aliases`、`links` 会按英文逗号、中文逗号或顿号拆分。因此，像“油斑、CCD与污染路径”这种含顿号的完整标题，不宜放在 `links` 字段；上例使用文章 ID `atlas_oil`。也可在正文写完整双链：

```text
links: 油斑, atlas_oil

相关知识：[[油斑]]、[[油斑、CCD与污染路径]]
```

复杂条件、证据数组、审核状态、FTA 逻辑不要塞进顶部元信息，写入正文模板。将来扩展加载器后，再进行明确版本的数据迁移。

当前文件大小限制为 512,000 字节，界面提示约 500 KB；最多加载 500 篇自建文章，正文至少 20 字符。以 `_` 或 `.` 开头的文件/目录、`README.md` 和非 MD/TXT 文件会被跳过。图片附件不会因为写在 MD 中就被转换成可检索的图中知识。

## 10. 三种案例都要具备的共同内容

最少包含：案例身份与状态、短摘要、适用与不适用条件、问题定义、事实与缺口、证据表、候选判断及判别检查、机制解释、质量控制点、控制不当后果、措施与验证、未解决问题、知识关联、变更记录。

信息不足时保留小节并明确写“未提供/待核验/不适用及原因”。空白不能让模型分辨是没有发生、没有测量还是整理遗漏。无效措施、复发、反例和被推翻的解释，同样值得入库。

## 11. 模板一：现场经验教训卡

复制下方模板时去掉外层代码围栏，填写实际信息。需要投递时，再添加第 9 节的兼容元信息。

```markdown
# LL-编号｜现象与学习点

## 案例身份与状态
```

## 13. 模板三：客诉 FTA 案例

FTA 是对一个明确事件的逻辑拆解。OR 表示任一输入事件发生即可使相应输出事件发生；AND 表示所列输入事件需要共同成立。逻辑门的正确性取决于事件定义和建模边界，不能把普通原因清单直接换成门符号。方法参考已查阅的 [NASA《Fault Tree Handbook with Aerospace Applications》](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)，第 3—4 章；该来源用于 FTA 方法，不用于证明隔膜案例结论。

```markdown
# FTA-编号｜顶事件的准确描述

## 身份、版本与状态
- 案例编号、组号、版本、文档状态：
- 原始树是否完整、事件/门逻辑是否经过复核：
- 本知识稿的结论状态：

## 顶事件定义
- 事件：何种对象在何种工况下出现何种可判定失效。
- 判据与检测方法：只保留可公开的定义。
- 顶事件在本案例中是否已有实物或测试证据：
- 客户报告的现象与本方已核验结果有什么差别：

## 系统与时间边界
材料结构、装配/热压/烘烤/注液等相关状态、检测条件、观察阶段。
供应前、运输储存、客户加工及使用阶段的范围；未知边界明确列出。

## 事件字典
| 事件号 | 事件名称及判据 | 类型：顶/中间/基本/未展开/条件 | 适用范围 | 当前状态 |
|---|---|---|---|---|
| T01 | 顶事件 | 顶事件 | 待填写 | 待核验 |
| E01 | 明确的不利事件，不能只填“设备” | 中间/基本等 | 待填写 | 待验证 |

## 逻辑门与树结构
| 门号 | 输出事件号 | 门类型 | 输入事件号 | 为什么是这种逻辑 | 尚未覆盖的路径 |
|---|---|---|---|---|---|
| G01 | T01 | AND/OR/未判定 | 用逗号列事件号 | 必须能用完整句子解释 | 未知不能写无 |

可附文本树或 Mermaid 图，但事件表和门表是结构主记录，不能只保留图片。
顺序依赖或复杂条件先写清楚；不要擅自转成普通 AND/OR。

## 各分支验证记录
| 事件/分支 | 成立时应见什么 | 判别方法与覆盖范围 | 已取得证据号 | 结论及不能排除的部分 |
|---|---|---|---|---|
| E01 | 预期 | 检查尚未做时明确标注 | 无/EVD01 | 待验证等 |

## 证据摘要
FTA事件号与证据号分开，证据用 EVD01 等编号，避免混淆。
记录观察、方法、位置、对照、限制、核验状态以及支持/反对的具体分支。

## 发生原因、流出原因与系统原因
- 发生原因：物理失效如何形成；未知时保留候选。
- 流出原因：在既定检验与拦截范围内为什么未被发现或处理；不能默认供应方漏检。
- 系统原因：哪些管理或设计环节允许上述问题持续；没有证据不能补写归责。
三类不强行放在同一层 OR 门下，是否进入同一树取决于顶事件定义。

## 与隔膜知识的对应
每个关键事件对应哪个工序/结构/物性/缺陷/电芯表现节点。
从客户现象回溯时，区分隔膜、电极、电解液、装配和检测等可能来源，按事件范围考虑。
没有中间证据，不能从某个外观缺陷直接跳到某个电芯后果。

## 措施、阻断位置与复验
说明措施阻断哪个事件或传播条件、怎样验证、还有哪些分支未覆盖。
短期未复发、单次未检出、客户结案分别记录，不等同全部路径排除。

## 可复用的诊断问题与停止条件
优先问哪个问题、为什么、回答不同如何分支；何时必须取得实物或实验结果。
当前没有足够数据时，不计算故障概率、贡献率或根因置信百分比。

## 关系变更与历史版本
说明哪些门和事件来自报告、哪些是整理建议，改动原因及审核状态。
保留被否定或停用分支及适用范围，避免后续重新误用。
```

## 14. 常见错误与修正要求

| 常见写法 | 问题 | 应改成什么 |
|---|---|---|
| “CCD 检出油斑，所以残油超标” | 外观标签被当成成分和定量结论 | 分别核对实物、位置、形貌、成分及适用的残油检测 |
| “A 品率上升，证明缺陷减少” | 判级、检出、分母或产品结构可能变化 | 先检查评价口径，再判断物理改善 |
| “调整后好了，因此该参数是根因” | 混杂、自然波动或组合措施未区分 | 表述关联，补对照和可区分验证 |
| “员工意识不足” | 不可直接验证，不能指导机理分析 | 写清具体动作、条件、防错/监测和流程缺口 |
| “未发现问题，该分支排除” | 不说明方法能力和覆盖范围 | 写“在这些样本和方法条件下未获得支持”，并列剩余范围 |
| “图谱上有连线，所以已经证明” | 关联与因果混淆 | 核对关系类型、适用条件及对应证据 |
| “其他报告也这样写，说明证据很多” | 可能都来自同一试验 | 登记案例组和证据组，去除重复计数 |

```text

1. 按类别模板组织的MD草稿；
2. 必须由人补充或复核的信息清单，按对结论影响排序；
```

## 16. 入库前逐项验收

- [ ] 案例类别、匿名编号、内容版本及状态齐全，未把生产日期与整理日期混淆。
- [ ] 没有把不同产品、路线、测法或时期的资料拼成一个事实链。
- [ ] 问题和评价口径明确，检测系统变化与实物变化分开。
- [ ] 事实、假设、机理补充及建议清楚区分，缺失信息没有被补造。
- [ ] 每条重要结论有适用条件、证据状态、替代解释或限制。
- [ ] 机制解释通顺，控制点可观察，失控后果不越过证据边界。
- [ ] 经验卡保留失败尝试；专项保留方法与混杂；FTA保留事件和门逻辑。
- [ ] 标题、正文、元信息、图片及附件引用均无内部识别信息或原始数据。
- [ ] 链接目标真实存在；新增关系明确标为候选；同源证据没有重复计数。
- [ ] 可检索的小节能独立读懂，没有只有“如上所述”的关键结论。
- [ ] 程序中展示、外部模型发送和发布导出三个范围分别核对，未默认为同一范围。
- [ ] 投递副本与主稿一致，并在程序同步后检查标题、检索、链接和材料包。

完成整理不代表自动完成专业审核。达到哪一步就记录哪一步；在事实有限时，清楚保存“为什么还不能下结论”，本身就是有价值的工程知识。
