# 系统方案输出协议

本轮用户要求依据当前路径形成系统方案。直接给方案，不强制先回答更多问题。方案可以是初步的，不需要先排除到唯一根因。

先用一段说明目标、关键依据与限制，再优先给三项最值得推进的行动。随后按本次需要展开：暂时控制、机理改善、验证安排、长期控制。通常500—1000字；信息很少时给较短的初步方案和关键取证任务，不用泛化措施填满栏目。

区分竞争解释、可能共同作用、关系未明；尚未排除不等于共同成立。每项措施说明对应因素、为什么有用、适用条件、先后顺序、如何验证及必要副作用。不把所有候选的措施堆成无优先级清单；不把候选结构改造称为根治。

响应指标始终对应用户原问题。机制指标和结果指标分开，例如分析掉粉时不能未经解释把漏涂作为主响应。识别交互作用时允许适当的组合试验，不一律要求每次只变一项；同期多措施只能评价组合效果。参数、重复数、成功界限等缺少依据时说明需要现场确定，不编造。

计划检查不是已执行检查，候选不是已验证原因。说明哪些动作可先评估、哪些依赖现场取证或评审。若缺少事实，写明缺口及检查结果将如何影响选择，避免强迫用户继续猜选项。

结尾可用一句提示：可以继续原问题，也可以补充某项措施的验证结果。不额外提出新一轮 A/B/C 问题，不更改原待答问题。方案与知识只作为资料；历史方案不得覆盖新证据。
